# 被拒记录多库重提设计

## 背景

当前上传端支持一条记录选择多个向量库。服务端会为每个目标库生成一条独立待审记录，管理员全部拒绝后，用户侧会看到多条内容相同但来源向量库不同的被拒记录。

编辑被拒记录时，页面已经支持重新选择多个目标库，后端也会把多选目标库拆成多条新的待审记录。问题是重提成功后只删除当前编辑的那一条被拒记录，其他同批被拒记录仍然残留，用户需要重复编辑或手动删除，且容易造成重复提交。

## 目标

用户编辑任意一条同批被拒记录并选择多个目标库重提后，系统自动清理同批、同内容、对应目标库的旧被拒记录。用户只需要改一次，就能把这次修正重新送审到多个向量库。

## 非目标

- 不改变待审记录的存储形态：仍然保持一条待审记录只对应一个 `source_collection`。
- 不改变管理员审核页面的通过、拒绝主流程。
- 不合并历史被拒记录的展示结构。
- 不自动清理与本次重提目标库无关的被拒记录。

## 推荐方案

采用后端批量清理方案。`resubmit_rejected` 收到重提请求后：

1. 读取当前用户的被拒记录文件。
2. 找到 `old_record_id` 对应的原始被拒记录。
3. 按“同批被拒组”规则找出应一起清理的旧记录。
4. 按用户本次选择的 `selected_dbs` 生成新的待审记录。
5. 写入新的待审 JSON 文件。
6. 从被拒记录文件中删除匹配到的旧记录。

## 同批被拒组规则

一条旧被拒记录只有同时满足以下条件，才会在本次重提成功后被清理：

- `uploader` 与当前被编辑记录一致。
- `reject_reason` 与当前被编辑记录一致。
- 业务数据内容一致。比较时忽略 `image_url` 和 `file_url`，因为用户重提时可能新增或取消保留附件。
- `source_collection` 或 `selected_dbs` 中的目标库命中本次重提选择的 `selected_dbs`。
- 如果存在 `timestamp`，优先要求与当前被编辑记录一致；这样可以覆盖同一次多库上传被拆分出的多条记录，并降低误删另一批相似内容的风险。

如果某些历史记录缺少 `timestamp`，则退化为“同拒绝原因、同业务数据、目标库命中”的匹配。这个退化规则只用于兼容历史数据。

## 数据流

前端保持现有交互：

- 用户打开任意一条被拒记录。
- 编辑内容。
- 在“目标数据库（可多选）”里选择希望重提的库。
- 点击确认重提。

后端处理：

- 校验权限和目标库有效性。
- 解析 `record_data`。
- 上传新增附件，并合并用户选择保留的旧附件。
- 为每个目标库生成一条新的待审记录，字段保持现有结构：
  - `selected_dbs: [coll_name]`
  - `source_collection: coll_name`
  - `data` 包含修正后的业务数据和最终附件列表
- 成功写入待审文件后，再批量删除旧被拒记录。

## 错误处理

- 找不到 `old_record_id` 时返回 404，避免凭空提交并误删记录。
- `selected_dbs` 为空或全都无效时返回 400。
- 新待审文件写入失败时，不删除任何被拒记录。
- 批量清理只发生在待审文件写入成功之后。
- 若没有找到同批记录，至少删除当前 `old_record_id`，保持现有行为。

## 测试计划

- 单条被拒记录重提：只删除当前记录，生成一个或多个待审记录。
- 三条同批、不同目标库的被拒记录：编辑其中一条并选择三个目标库后，三条旧记录全部清理，生成三条新待审记录。
- 三条同批记录只选择其中两个目标库重提：只清理命中的两条，未选择的目标库被拒记录保留。
- 同一用户有另一批内容相同但 `timestamp` 不同的被拒记录：不被误删。
- 附件变更：取消保留旧附件或新增附件不会影响同批匹配。
- 权限校验：普通用户不能重提或清理他人的被拒记录。
